## ADR-001: 编程语言选择 — Python

### 状态: ✅ 已接受 (Accepted)

### 背景

300 Agent 融合项目需要整合多个异构系统：Gemini Web API (Python 逆向库)、Google Workspace API、6 大视频生成模型 API。编程语言的选择直接影响技术栈兼容性、开发效率、生态成熟度和团队学习成本。

### 决策

选择 **Python 3.10+** 作为项目唯一编程语言。

### 后果

#### ✅ 正面影响

| 维度 | 说明 |
|------|------|
| **Gemini 生态兼容** | gemini-webapi (P0 主引擎) 是 Python 库，直接集成无需桥接 |
| **异步生态成熟** | asyncio + aiohttp 生态完善，支持全异步 I/O |
| **数据验证** | Pydantic v2 提供强类型数据模型，覆盖 18 个核心模型类 |
| **Google 官方支持** | google-auth / google-api-python-client 官方维护 |
| **AI/ML 生态** | 丰富的 VLM、向量检索、ML 库，路由算法未来可无缝升级 |
| **开发效率** | 快速迭代，融合项目预估 35-40 人天，Python 可压缩 20% |
| **运维友好** | 结构化日志 (loguru)、监控 (prometheus_client) 生态成熟 |

#### ⚠️ 负面影响

| 维度 | 说明 | 缓解措施 |
|------|------|----------|
| **GIL 限制** | CPU 密集型任务无法真正并行 | 图片分析等 CPU 任务使用异步 + 进程池 |
| **运行时性能** | 比 Go/Rust 慢 10-50x | 热点路径用 Cython / 异步 I/O 规避 |
| **类型安全** | 运行时检查，非编译期 | 全项目使用 Pydantic + mypy 静态检查 |

### 替代方案

| 语言 | 评分 | 放弃原因 |
|------|:----:|----------|
| **Node.js/TypeScript** | 6/10 | gemini-reverse 为 Node.js，但生态评分仅 5.67；异步模型不同；Pydantic 无等价物 |
| **Go** | 5/10 | 无原生 Gemini 库；Google API 客户端成熟但视频模型 SDK 缺失；开发效率低 |
| **Rust** | 3/10 | 学习成本极高；开发周期翻倍；AI 生态不成熟 |

### 关键证据

```
fusion-gemini-group 评分对比:
- gemini-webapi (Python):    8.80 / 10  → P0 主引擎
- gemini-web-mcp-cli (Python): 7.25 / 10  → P1 参考
- gemini-reverse (Node.js):  5.67 / 10  → P2 备选

fusion-api-layer 技术可行性评分: 8/10
"Python asyncio 生态成熟，各系统均有异步接口"
```

## ADR-002: Gemini 库选择 — gemini-webapi

### 状态: ✅ 已接受 (Accepted)

### 背景

项目需要与 Google Gemini 交互（提示词生成、图片分析、Gem 管理）。三个候选库各有优劣：gemini-webapi (Python)、gemini-web-mcp-cli (Python)、gemini-reverse (Node.js)。

### 决策

选择 **gemini-webapi** 作为底层核心引擎，通过 **BaseGeminiProvider 抽象接口 + WebapiAdapter** 接入系统。

### 后果

#### ✅ 正面影响

| 维度 | 说明 |
|------|------|
| **核心功能 100% 覆盖** | 18/18 核心功能完整支持 |
| **技术最成熟** | curl_cffi TLS 指纹模拟 + Watchdog 流式断线恢复 |
| **社区活跃** | 3.3k stars, 22 contributors, 2 年维护历史 |
| **有测试覆盖** | 三个候选中唯一有单元测试 |
| **动态模型发现** | 运行时自动获取最新模型列表 |

#### ⚠️ 负面影响

| 维度 | 说明 | 缓解措施 |
|------|------|----------|
| **AGPL-3.0 许可证** | 商用闭源存在合规风险 | **独立服务部署**：gemini-webapi 封装为独立 AGPL 服务，通过 HTTP/gRPC 通信 |
| **代码质量债务** | 部分方法 >600 行 | Adapter 层隔离，不直接修改源码 |
| **Cookie 认证脆弱** | 非官方 API，随时可能失效 | 3 层恢复机制 + 健康检查 |

### 替代方案

| 方案 | 评分 | 放弃原因 |
|------|:----:|----------|
| **gemini-web-mcp-cli 直接依赖** | 放弃 | Alpha 状态；仓库 404 不可访问；供应链风险极高 |
| **gemini-reverse 主方案** | 放弃 | 项目仅 1 周历史；Node.js 技术栈；无测试/无 CI |
| **Google 官方 Gemini API** | 备选 | 成本高昂；功能受限；不支持 Gem |

### 架构隔离方案 (AGPL 合规)

```python
# AGPL 隔离: gemini-webapi 作为独立服务
gemini_service/main.py          # AGPL-3.0 授权，独立进程
main_project/gemini_client.py   # 主项目闭源，通过 HTTP 调用
```

### 关键证据

```
融合决策矩阵:
- 综合评分: gemini-webapi 8.80 > mcp-cli 7.25 > reverse 5.67
- 核心功能覆盖: webapi 100% > reverse 89% > mcp-cli 83%
- 生态成熟度: webapi 9.0 > mcp-cli 5.5 > reverse 3.0
- 融合策略: gemini-webapi 直接集成(P0), mcp-cli 组件借用(P1), reverse 降级备选(P2)
```

## ADR-003: 视频模型集成策略 — 适配器模式

### 状态: ✅ 已接受 (Accepted)

### 背景

系统需集成 6 大视频生成提供商（即梦/可灵/Vidu/Veo/Runway/Pika），每家 API 接口、认证方式、参数格式、返回结构完全不同。需要一个统一策略来降低集成复杂度和未来扩展成本。

### 决策

采用 **适配器模式 (Adapter Pattern)**，设计 `UnifiedVideoGenerator` 统一抽象层，每个模型实现独立适配器。

```
                    ┌─────────────────────────┐
                    │  UnifiedVideoGenerator  │  ← 统一接口
                    │  (抽象基类)              │
                    └───────────┬─────────────┘
                                │
            ┌───────────┬───────┼───────┬───────────┐
            ▼           ▼       ▼       ▼           ▼
      ┌─────────┐ ┌─────────┐ ┌─────┐ ┌─────┐ ┌─────────┐
      │ Kling   │ │ Veo     │ │Seed │ │Vidu │ │ Runway  │
      │Adapter  │ │Adapter  │ │Adap │ │Adap │ │ Adapter │
      └────┬────┘ └────┬────┘ └─┬───┘ └─┬───┘ └────┬────┘
           │           │        │       │           │
      ┌────▼────┐ ┌────▼────┐ ┌─▼───┐ ┌─▼───┐ ┌────▼────┐
      │Kling API│ │Veo API  │ │Seed │ │Vidu │ │Runway   │
      └─────────┘ └─────────┘ └─────┘ └─────┘ └─────────┘
```

### 后果

#### ✅ 正面影响

| 维度 | 说明 |
|------|------|
| **新增模型零改动** | 新增模型只需实现适配器，不修改现有代码 (开闭原则) |
| **统一返回格式** | 所有提供商返回 `VideoResult` Pydantic 模型 |
| **错误归一化** | 统一错误码映射，统一异常处理 |
| **成本可控** | 预估开发成本 2-3 人周，月度运营成本节省 30-60% |
| **核心功能 100% 覆盖** | 文生/图生/参考生/首尾帧/延长 5 大功能全覆盖 |

#### ⚠️ 负面影响

| 维度 | 说明 | 缓解措施 |
|------|------|----------|
| **维护负担** | 6 个适配器需同步跟进 API 变更 | 适配器隔离 + 单元测试覆盖 |
| **功能阉割** | 取交集可能丢失特有功能 | `extra_params` 透传提供商特有参数 |
| **性能开销** | 抽象层增加一次调用转发 | 抽象层为纯 Python，开销 < 1ms |

### 替代方案

| 方案 | 放弃原因 |
|------|----------|
| **直接调用各 API** | 重复代码 80%+；新增模型需修改核心业务逻辑 |
| **统一 REST 网关** | 增加部署复杂度；不适合 Skill 嵌入式场景 |
| **GraphQL 联邦** | 过度设计；各提供商无 GraphQL 接口 |

### 关键证据

```
fusion-video-models 分析结论:
- 分析模型/版本数: 8个核心模型版本（跨6家提供商）
- 统一接口覆盖率: 核心功能100%
- 预估融合开发成本: 2-3人周
- 预估月度运营成本节省: 30-60%（通过智能选型）
- 融合策略: 适配封装为主(5/6)，直接集成(1/6)
```

## ADR-004: 数据存储选择 — Google Sheets

### 状态: ✅ 已接受 (Accepted)

### 背景

系统需要存储两类核心数据：(1) Gem 模板元数据（动态增长的配置数据）(2) 任务调度状态（批量任务的实时追踪）。需要考虑非技术用户的可维护性、已有基础设施复用、协作编辑能力。

### 决策

选择 **Google Sheets** 作为核心数据存储，通过 **Pydantic 模型 + Sheets 序列化层** 实现类型安全的数据交互。

- **gem-metadata 表**: Gem 模板配置（品类/人群/场景/风格匹配维度）
- **task-queue 表**: 批量任务状态追踪
- **batch-summary 表**: 批次汇总统计

### 后果

#### ✅ 正面影响

| 维度 | 说明 |
|------|------|
| **非技术用户友好** | 运营人员可直接编辑 Sheets 调整 Gem 配置，零代码 |
| **协作编辑** | 多人实时协作，天然支持版本历史 |
| **零基础设施** | 无需部署数据库，复用 Google Workspace |
| **新增 Gem 零代码** | 在 Sheets 中添加一行配置即可生效 |
| **可视化** | 任务状态一目了然，支持条件格式 |

#### ⚠️ 负面影响

| 维度 | 说明 | 缓解措施 |
|------|------|----------|
| **并发写入限制** | Sheets API 100秒/100用户 限制 | batchUpdate + 指数退避 |
| **查询能力弱** | 无索引，大数据量查询慢 | 本地缓存 + 增量同步 |
| **数据一致性** | 无事务支持 | 乐观锁 + 状态机验证 |
| **行数上限** | 1000 行/Sheet（Gem 元数据足够，任务表需归档） | 定期归档到历史表 |

### 替代方案

| 方案 | 放弃原因 |
|------|----------|
| **PostgreSQL** | 需要部署维护；非技术用户无法直接编辑 |
| **MongoDB** | 同 PostgreSQL；Schema-less 增加数据验证复杂度 |
| **Firebase/Firestore** | 额外成本；Google Sheets 已满足需求 |
| **本地 SQLite** | 不支持多机协作；运营人员无法访问 |

### 关键证据

```
fusion-data-models 分析:
- Pydantic 模型类: 18个（覆盖全量数据结构）
- Google Sheets 表: 2张（gem-metadata + task-queue）
- 序列化/反序列化函数: 12个
- 新增 Gem 成本: 0代码（仅 Sheets 添加行）

fusion-workspace 功能匹配:
- gws sheets +read:    100% 匹配
- gws sheets +append:  100% 匹配
- gws drive +upload:   100% 匹配
```

## ADR-005: Workspace 工具选择 — gws CLI

### 状态: ✅ 已接受 (Accepted)

### 背景

系统需与 Google Workspace（Sheets/Drive/Gmail）交互，有两种技术路径：使用 Google 官方 Python Client 库，或使用 gws CLI 工具。

### 决策

选择 **gws CLI (googleworkspace/cli)** 作为 Workspace 集成工具，通过子进程调用封装为 Python Skill 组件。

### 后果

#### ✅ 正面影响

| 维度 | 说明 |
|------|------|
| **代码量极少** | 一行命令替代 20-50 行 Python 代码 |
| **认证管理完善** | 自动从凭证存储获取，自动刷新 Token |
| **JSON 原生输出** | `--format json` 直接返回结构化数据 |
| **Helper 命令** | `+read` / `+append` / `+send` 等语法糖 |
| **分页自动处理** | `--page-all` 自动处理 nextPageToken |
| **MIME 自动推断** | Drive 上传自动推断 MIME 类型 |

#### ⚠️ 负面影响

| 维度 | 说明 | 缓解措施 |
|------|------|----------|
| **子进程开销** | 每次调用 fork 子进程 (~50ms) | 批量操作聚合；缓存热数据 |
| **版本 pre-v1** | gws v0.22.5 为 pre-release | 锁定版本；API 兼容性测试 |

| **无原生 Python API** | 无法直接 import 调用 | 封装 `GWSClient` 类提供异步接口 |

| 方案 | 放弃原因 |
|------|----------|

| **直接 REST API 调用** | 重复造轮子；认证逻辑复杂 |

### 关键证据

```

┌─────────────────┬─────────────────┬─────────────────────────┐
```

## ADR-006: 认证策略 — Service Account + API Key + Cookie

### 状态: ✅ 已接受 (Accepted)

### 背景

系统需与 6 大异构服务交互，涉及 5 种认证方式：Cookie (Gemini)、Service Account (Workspace)、API Key (视频模型)、OAuth2 (开发调试)、Bearer Token。需要统一策略管理多服务认证。

### 决策

采用 **分层认证管理架构**，按服务类型选择最优认证方式：

| 服务 | 认证方式 | 理由 |
|------|----------|------|
| **Google Workspace** | Service Account | 服务器环境标准做法；无浏览器依赖；域级授权 |
| **视频模型 API** | API Key | 各提供商标准方式；简单可靠 |
| **Gemini Web** | Cookie | gemini-webapi 唯一支持方式；3层恢复机制保障 |
| **开发调试** | OAuth2 | 仅开发环境使用；P1 优先级 |

统一抽象：`AuthManager` + `AuthStrategy` 策略模式，支持 5 种认证方式统一管理。

### 后果

#### ✅ 正面影响

| 维度 | 说明 |
|------|------|
| **自动化运行** | Service Account 无需人工干预，适合服务器环境 |
| **安全隔离** | 敏感信息加密存储（密钥环/加密文件/环境变量） |
| **统一接口** | 所有认证通过 `AuthManager.get_auth_headers()` 获取 |
| **自动刷新** | Service Account Token 1小时过期自动刷新 |
| **凭证健康检查** | 定时验证所有凭证有效性 |

#### ⚠️ 负面影响

| 维度 | 说明 | 缓解措施 |
|------|------|----------|
| **Cookie 脆弱性** | Gemini Cookie 随时可能失效 | 3层恢复机制：(1)自动刷新 (2)browser-cookie3加载 (3)多层备选 |
| **凭证泄露风险** | Service Account JSON 文件泄露后果严重 | 密钥环存储 + 最小权限原则 |
| **多凭证管理复杂** | 6个服务需管理多组凭证 | 统一凭证注册表 + 自动验证 |

### 替代方案

| 方案 | 放弃原因 |
|------|----------|
| **统一 OAuth2** | Gemini 不支持；视频模型无 OAuth2 接口 |
| **仅 Cookie 认证** | Workspace 需要 Service Account；视频模型需要 API Key |
| **Vault 企业方案** | 过度设计；当前规模不需要 HashiCorp Vault |

### 关键证据

```
fusion-auth-security 分析:
- 分析范围: 6大服务认证体系
- 认证类型: 5种 (Cookie/ServiceAccount/APIKey/OAuth2/Bearer)
- 融合策略: 适配封装
- 安全存储: 分层存储 (密钥环 > 加密文件 > 环境变量)
```

## ADR-007: 路由算法选择 — 规则引擎 vs ML模型

### 状态: ✅ 已接受 (Accepted)

### 背景

智能路由引擎需将产品图片分析结果映射到最合适的 Gem 模板。核心挑战：维度爆炸（产品/人群/场景/风格多维交叉）、Gem 动态增长、置信度控制、计算性能。

### 决策

选择 **规则引擎（加权多维匹配）** 作为主算法，**ML 模型** 作为 P1 增强（自学习权重调整）。

```
路由算法架构:
┌─────────────────────────────────────────────┐
│  策略模式: IMatchStrategy                    │
│  ├── StandardStrategy  (P0) — 完整14维分层过滤 │
│  ├── FastStrategy      (P0) — 快速8维硬过滤   │
│  ├── SemanticStrategy  (P1) — 向量语义匹配    │
│  └── EnsembleStrategy  (P1) — 多策略融合加权  │
└─────────────────────────────────────────────┘
```

**加权评分公式** (14 维度):

| 维度组 | 权重 | 子维度 |
|--------|:----:|--------|
| 产品维度 | **40%** | 品类(15%) + 类型(8%) + 价格带(7%) + 品牌调性(5%) + 卖点(5%) |
| 人群维度 | **23%** | 性别(8%) + 年龄(7%) + 消费力(5%) + 画像(3%) |
| 场景维度 | **25%** | 营销场景(12%) + 使用场景(8%) + 平台(5%) |
| 风格维度 | **12%** | 视频风格(8%) + 画面调性(4%) |

**置信度三级体系**:
- **HIGH** (>= 0.85): 直接推荐 Top-1
- **MEDIUM** (0.70-0.85): 推荐 Top-3，用户选择
- **LOW** (< 0.70): 兜底策略 + 记录反馈

### 后果

#### ✅ 正面影响

| 维度 | 说明 |
|------|------|
| **可解释性强** | 每步匹配逻辑清晰透明，便于调试和优化 |
| **零训练数据** | 无需历史数据即可运行，冷启动友好 |
| **延迟低** | P99 < 100ms（不含图片分析） |
| **新增 Gem 零代码** | 元数据自描述，自动适配匹配 |
| **权重可调** | 运营人员可通过 Sheets 调整权重配置 |
| **ML 可升级** | P1 自学习机制根据反馈自动优化权重 |

#### ⚠️ 负面影响

| 维度 | 说明 | 缓解措施 |
|------|------|----------|
| **人工调参** | 14 维度权重需人工设定初始值 | 基于业务经验预设 + 自学习自动调整 |
| **复杂场景局限** | 极端复杂匹配可能不如 ML | SemanticStrategy (P1) 补充 |
| **冷启动质量** | 初始权重可能不是最优 | A/B 测试 + 快速迭代 |

### 替代方案

| 方案 | 放弃原因 |
|------|----------|
| **端到端 ML 模型** | 需要大量标注数据；训练成本高；可解释性差；冷启动困难 |
| **向量检索 (RAG)** | 单独使用效果不佳；作为 P1 增强策略组合使用 |
| **规则硬编码** | 无灵活性；无法自适应 |

### 关键证据

```
fusion-smart-router 设计指标:
- 路由延迟目标: < 100ms (P99，不含图片分析)
- 高置信度占比目标: > 70%
- 匹配准确率目标: > 85%
- 扩展成本: 零代码（新增 Gem 无需修改代码）
- 核心算法: 分层降维 + 权重动态调整
```

## ADR-008: 异步架构 — asyncio vs 线程池

### 状态: ✅ 已接受 (Accepted)

### 背景

系统存在大量 I/O 密集型操作：6 个视频 API 调用、Google Sheets/Drive API、Gemini 对话、异步轮询。需要选择合适的并发模型来最大化吞吐量和资源利用率。

### 决策

选择 **asyncio** 作为核心异步框架，**全异步 I/O** 设计。

```
异步架构分层:
┌─────────────────────────────────────────────┐
│  Layer 4: 业务层 (async)                     │
│  ├── TaskController — 批量任务并发调度         │
│  ├── SmartRouter — 路由匹配                  │
│  └── PromptBuilder — 提示词生成              │
├─────────────────────────────────────────────┤
│  Layer 3: 服务层 (async)                     │
│  ├── GeminiClient — Cookie 认证 + SSE 流式   │
│  ├── VideoGenerator — 异步 API 调用          │
│  └── GWSClient — 子进程异步封装              │
├─────────────────────────────────────────────┤
│  Layer 2: 基础设施层 (async)                 │
│  ├── AsyncTaskPoller — 指数退避轮询          │
│  ├── RateLimiter — 异步令牌桶               │
│  └── RetryEngine — 异步重试 + 熔断           │
├─────────────────────────────────────────────┤
│  Layer 1: 并发控制                           │
│  ├── asyncio.Semaphore — 全局/阶段并发       │
│  ├── asyncio.create_subprocess — gws 调用    │
│  └── asyncio.TaskGroup — 批量任务管理        │
└─────────────────────────────────────────────┘
```

### 后果

#### ✅ 正面影响

| 维度 | 说明 |
|------|------|
| **I/O 利用率最大化** | 单线程处理数千并发连接，无 GIL 竞争 |
| **代码简洁** | async/await 语法直观，比回调地狱易读 |
| **生态成熟** | aiohttp/tenacity/asyncio 生态完善 |
| **视频轮询天然适配** | 异步轮询框架完美适配视频生成异步 API |
| **全链路追踪** | 异步上下文变量实现请求级日志关联 |

#### ⚠️ 负面影响

| 维度 | 说明 | 缓解措施 |
|------|------|----------|
| **CPU 密集型阻塞** | 图片分析等 CPU 任务会阻塞事件循环 | CPU 任务使用 `asyncio.to_thread()` 或进程池 |
| **调试困难** | 异步栈跟踪复杂 | 结构化日志 + trace_id 全链路追踪 |
| **第三方库兼容** | 部分库不支持异步 | 线程池包装或选择异步替代品 |
| **学习曲线** | 团队需掌握异步编程模式 | 代码审查 + 异步最佳实践文档 |

### 替代方案

| 方案 | 放弃原因 |
|------|----------|
| **线程池 (concurrent.futures)** | 数千连接时线程开销大；GIL 限制真正并行；上下文切换成本高 |
| **多进程** | 内存开销大；进程间通信复杂；不适合 I/O 密集场景 |
| **Go goroutine** | 语言已确定为 Python；Go 的 Gemini 生态不成熟 |

### 关键证据

```
fusion-api-layer 技术评估:
- 技术可行性评分: 8/10
- "Python asyncio 生态成熟，各系统均有异步接口"
- 开发效率提升: 60%+

fusion-batch-task 并发架构:
- 全局并发: asyncio.Semaphore(3)
- 阶段并发: 分析5 / 路由10 / 提示词3 / 视频5
- 视频轮询: 指数退避 + 超时兜底(10分钟)
```

## ADR-009: 错误处理策略 — 异常体系 + 降级链

### 状态: ✅ 已接受 (Accepted)

### 背景

系统依赖 6+ 外部服务，任何服务故障都可能导致视频生成功能不可用。需要设计统一的错误处理体系，确保系统在各种故障场景下都能优雅降级。

### 决策

采用 **统一异常体系 + 三级降级链 + 熔断保护** 的综合策略。

#### 统一异常体系 (7大类 40+ 错误码)

```
SkillException (基类)
├── ClientError (C开头 — 不重试)
│   ├── ValidationError (C002), AuthError (C101), QuotaExceededError (C301)
├── ServerError (S开头 — 可重试)
│   ├── RateLimitError (S001), ServerOverloadedError (S002)
├── NetworkError (N开头 — 可重试)
│   ├── ConnectionTimeoutError (N001), ReadTimeoutError (N002)
├── TaskError (T开头 — 部分可重试)
│   ├── VideoGenerationError (T104), AllProvidersFailedError (T201)
├── ResourceError (R开头)
├── ConfigurationError (F开头)
└── SystemError (E开头)
```

#### 三级降级链

```
Level 1: 模型级降级 (同一 Provider 内)
  Seedance 2.0 Pro → Seedance 2.0 Fast → Seedance 2.0 Mini
  
Level 2: Provider 级降级 (切换到不同提供商)
  Seedance 2.0 → Kling 3.0 → Veo 3.1 → Vidu Q3
  
Level 3: 服务级降级 (功能降级)
  实时生成 → 异步队列 → 预生成模板
  高清视频 → 标清视频 → 静态图片
```

#### 熔断器参数

| 参数 | 默认值 | 说明 |
|------|:------:|------|
| 失败率阈值 | 50% | 10次请求中失败5次触发熔断 |
| 熔断持续时间 | 30s | 断开状态持续30秒 |
| 半开探测数 | 3 | 半开状态允许3个探测请求 |

### 后果

#### ✅ 正面影响

| 维度 | 说明 |
|------|------|
| **错误处理一致性** | 所有模块使用统一异常体系，消除重复逻辑 |
| **自动故障恢复** | 三级降级链自动切换，用户无感知 |
| **防止级联故障** | 熔断保护避免故障扩散 |
| **用户体验提升** | 错误提示从"500 Internal Error"变为"已自动切换到备用服务" |
| **可观测性增强** | 全链路日志 + 40+ 错误码精准定位问题 |

#### ⚠️ 负面影响

| 维度 | 说明 | 缓解措施 |
|------|------|----------|
| **降级质量下降** | 降级后视频质量可能降低 | 明确告知用户降级情况 |
| **成本不确定性** | 不同 Provider 定价不同 | CostMonitor 实时监控 |
| **复杂度增加** | 三级降级链 + 熔断逻辑增加代码复杂度 | 集中封装在 FailoverManager |

### 替代方案

| 方案 | 放弃原因 |
|------|----------|
| **各模块独立错误处理** | 错误处理分散，无统一入口；重复代码 70%+ |
| **简单重试 (固定间隔)** | 无法处理多 Provider 故障；无熔断保护 |
| **全局兜底 (try-except)** | 掩盖真正问题；无法精准恢复 |

### 关键证据

```
fusion-error-handling 评估:
- 综合评分: 9.2/10 — 强烈推荐优先实施
- 错误处理统一化: 重复代码降低 70%+
- 系统可用性: 从 99% 提升至 99.9%
- 问题定位: 从小时级降至分钟级
- 用户提示: "视频生成服务暂时繁忙，已自动切换到Kling，预计2分钟完成"
```

## ADR-010: 配置管理 — 分层配置架构

### 状态: ✅ 已接受 (Accepted)

### 背景

系统有大量配置项：API Keys、Cookie、Sheets ID、视频模型参数、路由权重、并发设置。配置来源多样（代码默认值、用户配置文件、环境变量、命令行参数），需要统一策略管理。

### 决策

采用 **四层叠加配置模型**，高层覆盖低层。

```
优先级: 最高 ←─────────────────────────────────────────→ 最低

┌──────────┐
│ 第4层    │  命令行参数 (CLI Arguments)
│ CLI      │  · --provider kling_3_0 --concurrency 5
│          │  · 一次性覆盖、调试场景
├──────────┤
│ 第3层    │  环境变量 (Environment Variables)
│ ENV      │  · BATCH_VIDEO_PROVIDER_API_KEY=xxx
│          │  · CI/CD、容器化部署、敏感信息注入
├──────────┤
│ 第2层    │  用户配置文件 (~/.batch-video-skill/config.json)
│ USER     │  · 持久化用户偏好
│          │  · 支持注释（JSON with comments）
├──────────┤
│ 第1层    │  默认配置 (Code Defaults)
│ DEFAULT  │  · 代码内置，不可变
│          │  · 保证任何情况下系统可用
└──────────┘
```

**合并规则**:
1. 字典字段递归合并（非覆盖）
2. 列表字段完全替换（不合并）
3. 标量字段直接覆盖
4. `None` 值表示"使用默认值"，不参与覆盖

**核心组件**:

| 组件 | 类名 | 职责 |
|------|------|------|
| 配置管理器 | `ConfigManager` | 统一入口，协调各组件 |
| 配置验证器 | `ConfigValidator` | Pydantic Schema 校验 |
| 安全存储 | `SecureVault` | 敏感信息加密存储 |
| 变更发布器 | `ConfigWatcher` | 文件监听、热重载 |
| 配置代理 | `ConfigProxy` | 类型安全的配置访问 |

### 后果

#### ✅ 正面影响

| 维度 | 说明 |
|------|------|
| **配置来源清晰** | 4 层优先级明确，无冲突困惑 |
| **环境适配** | 开发(USER) / 测试(ENV) / 生产(ENV+CLI) 无缝切换 |
| **敏感信息安全** | API Key/Cookie 通过环境变量或密钥环注入，不落盘 |
| **热更新支持** | P1 权重、并发等配置运行时热更新，无需重启 |
| **Schema 验证** | 启动即验证，配置错误早发现 |

#### ⚠️ 负面影响

| 维度 | 说明 | 缓解措施 |
|------|------|----------|
| **合并逻辑复杂** | 递归合并 + None 处理增加理解成本 | 文档化 + 单元测试覆盖 |
| **优先级混淆** | 4 层优先级可能让开发者困惑 | 明确文档 + 日志输出最终配置来源 |
| **热更新风险** | 运行时配置变更可能导致意外行为 | 验证后应用 + 回滚机制 |

### 替代方案

| 方案 | 放弃原因 |
|------|----------|
| **单一配置文件** | 无法区分环境；敏感信息泄露风险 |
| **仅环境变量** | 配置项过多时管理困难；非技术用户不友好 |
| **配置中心 (etcd/Consul)** | 过度设计；当前为单机 Skill，无需分布式配置 |

### 关键证据

```
module-config 设计目标:
- 配置分层加载: P0 — 默认 → 用户 → 环境变量 → 命令行
- Schema 验证: P0 — Pydantic 强类型校验，启动即验证
- 安全存储: P0 — 敏感信息加密存储，支持密钥环
- 动态热更新: P1 — 运行时权重、并发等配置热更新
- 配置变更通知: P1 — 订阅/发布模式
```
